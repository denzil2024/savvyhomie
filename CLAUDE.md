# SavvyHomie — How We Work

This file is git-tracked and loads automatically in every Claude Code session on this repo, on any machine. It exists because Claude's own session memory lives in a local app-data folder tied to one machine and does NOT travel with `git clone` — this file is the fix, so a fresh laptop picks up the full working relationship, not just the code.

**Read order for a new session:** this file (auto-loaded) → `FOUNDATION.md` in full (current build state, design system, the full Phase 1-9 production workflow, dated status log) → `CONTENT-PLAN.md` (the master keyword list, what's published vs. next) → for pin work, run `node scripts/pin-tracker.mjs` live, never trust a stale note. This file covers durable process/style/personality rules that don't change session to session; FOUNDATION.md covers current state, which does.

## Project

SavvyHomie: home & kitchen product roundups + gift guides, monetized via display ads (Journey by Mediavine → Mediavine → Raptive) plus Amazon Associates. Zero photography budget — that constraint is why the niche is product roundups (Amazon SiteStripe images, free and legitimate) rather than original-photo content. Stack: React + Vite, SSR-prerendered to static HTML, Railway hosting + Cloudflare DNS. Audience: mostly female, US/UK/CA/AU, Pinterest-first traffic in months 1-12.

## Communication style / personality

- **Time-poor, wants a decisive partner, not analysis.** Keep replies to a few short sentences during active work. Make the call and state it; mention at most one risk in one line. Don't present multiple options side by side in plain text either — pick one path and give only that.
- **Decide firmly — reject bad options AND commit to a pick among the good ones, not just a list of rejections.**
- **AskUserQuestion:** a long-standing hard rule against ever using it was later observed being used twice for genuine one-time structural/creative forks (format choice, cover template) without pushback — treat that as a narrow, high-value exception (one clear question, a recommended option marked), not a green light to use it routinely. Default to stating a firm recommendation in plain text.
- **Never editorialize about the owner's personal life, wellbeing, or schedule** — no "get some rest," no comments outside the work itself, even in a closing line.
- **"A real audit" means only real, controllable findings.** Don't pad a report with expected/structural non-issues to sound thorough (e.g. "few pins on a brand-new board" isn't a finding). Verify a claim before asserting it as wrong — don't eyeball two things as "the same" without checking.
- **When handed exact replacement text, paste it verbatim.** Don't silently fix punctuation/grammar in one edit and not another — if something looks like a real error, ask before changing it, and handle the same kind of input the same way every time in a session.
- **Don't prescribe choices that are the owner's to make** (e.g. which exact reference image to attach to an AI prompt) even when trying to be thorough — state the constraint, let them supply the specifics, unless they invite either approach.

## Item-count / research rhythm (recurs on every new post)

- **Show the real research numbers AND state a firm recommended count together.** Presenting only raw data with no recommendation reads as unhelpful ("So?"). Skipping straight to a decision without ever showing the count was agreed reads as unaccountable ("Where is the research and did we even agree on the number?"). The right shape: real average from research → a specific firm number grounded in it → stop and let the owner confirm or override.
- **The owner's final number is often well above the real research average** — research sets category logic and direction, it doesn't cap the final count. A real average of ~11-15 for a narrow spoke keyword routinely lands at 25-33 once the owner applies the site's own spoke-size convention. Don't assume a low real average means a low final pick.
- **Item count must be genuinely re-derived every time, never matched to a sibling post's number or a habitual default** (e.g. "12-15 for a spoke" as a reflex). State the real mean/median from the actual competitor research first.
- **When a topic's later spokes hit real content exhaustion against earlier siblings, reduce the count honestly** — a smaller real list beats a padded fake one or a skip.

## Real top-10 research — the hard floor

- **Always pull and work through the real top 10 search results before drawing any conclusion (item count, intent, categories) — never stop at 2-4 because the first couple looked sufficient.** This has recurred repeatedly and gotten sharper each time, most recently: successfully fetching 4-5 of ~10-13 URLs found and presenting that as "the research," with no accounting of the rest, was caught directly. **The fix is closing the loop on sources already found, not searching more:** go back through every URL both searches surfaced and either fetch-and-use it or give an explicit discard reason — brand/service lead-gen page (confirm by fetching and checking for a consultation CTA/zip-code form), retailer catalog page, duplicate republish of another source, or unreachable after a real retry (SSL error, closed socket, 403/451 — expected noise, not a reason to move on silently). Present this as a visible source-by-source table, not a narrative summary.
- **More sources can genuinely overturn a conclusion, not just add confidence to one already reached.** A 3-source read can miss a real ~8-9-item genuinely-new product pool, or move a mean from ~13 to ~18. Keep pulling fresh URLs until ~10 have actually been attempted, even through repeated 403/404s — don't let tool-level fetch failures become an excuse to stop early.
- **Before recommending a skip, dig one level deeper for a genuinely different real-world variant of the search intent** before concluding there's no content ("small bedroom closet" first read as a near-duplicate of "small closet," a second pass testing "bedrooms with NO closet at all" found a real, distinct, well-covered cluster). Two skip recommendations in a row is itself a signal to slow down, not a pattern to continue.
- **A keyword's real intent can be structurally incompatible with the site's format** (e.g. "DIY Small Closet Organizer" turned out to be a from-scratch woodworking build tutorial, not an organizing-product roundup) — the fix is substituting the next keyword in the same sub-cluster, not forcing the format.
- **Category axis must be derived fresh per keyword, never reused from the last spoke just because it worked.** Real axes found across one sub-cluster alone: storage-mechanism (Cabinets/Drawers/Pantry/etc.), TYPE of the thing itself (pantry type: corner/closet-style/apartment/walk-in), sequential PROCESS (declutter → zone → containers → label → floor), converted/repurposed-space framing (specific to "tiny" vs. "small"), and depth/position-on-shelf (specific to a "deep shelves" keyword). Categories must group by what the item DOES for the reader, never by a meta-attribute like how it was sourced ("hacked vs. bought" is not a category).
- **Near-duplicate SERP = flag it, then differentiate using a real signal from the SAME research, never an invented workaround.** When a spoke's real top-10 nearly duplicates an already-planned sibling's (same domains re-ranking), say so explicitly rather than quietly building a second post that reads like the first with different item numbers.
- **Every new item list needs a duplicate-function self-audit, both within itself and against every prior list in the same topic** — not an eyeball read, actually list out anything that's the same physical product type even under different marketed framing.
- **Every product/search-term name needs a real-Amazon-searchability check as its own explicit step:** favor the plain/generic form over a precise-sounding styling adjective unless that adjective is common real listing language ("gemstone ring" over "statement cocktail ring"); avoid invented phrases, over-niche names, and anything that's really custom carpentry, not a purchasable product. Search-term entries must be short, single-concept, no slash-joined alternatives — that's literally what gets typed into Amazon's search bar.
- **Before evaluating or touching ANY keyword, read its actual research section in FOUNDATION.md/CONTENT-PLAN.md first** — don't improvise a methodology from a different niche's process. DIY/Organization content gets a real SERP+indie-blog check; Amazon-roundup categories (Kitchen Finds, Gift Guides, Everyday Home Finds) confirm on real Keyword Planner volume + on-topic + non-duplicate + genre-fit alone, no SERP check.

## Writing voice & style — read before writing or proofreading ANY post copy

**Absolute bans, everywhere (titles, meta, body, UI copy, Pinterest copy) — grep case-insensitively, including frontmatter, before calling anything done:** em-dashes (—, restructure into two sentences or a comma instead); "really," "actually," "genuinely"; "most" used as a crutch; "land(s)" used metaphorically; "spans"; "instead" used as a standalone sentence-opening transition (comparative "instead of A, B" mid-sentence is fine); "upgrade," "game changer," "must-have," "perfect for," "versatile," "convenient," "thoughtfully designed," "durable construction," "premium quality." **Any word that gets a strong "I hate this" reaction is an instant permanent add to this list** ("usually" hit 30 instances in one post before being banned; the first grep to check it missed capitalized instances for lack of `-i`, a recurring gotcha — always grep -i, and re-run after the fix, since a fix pass can silently overshoot into a new problem at a worse rate than the original).

**No "review-site" positioning** — warm curated-shopping-guide voice, not a Wirecutter-style testing-lab voice (no "tested"/methodology badges). American-focused, casual, conversational — write like a real person talking to a friend, never corporate-editorial polish or the flat over-explained rhythm that reads machine-written. H2 headings sitewide use Title Case.

**No colon-then-3+-item-list construction** ("the same problems: a drawer that won't close, a cable mess behind the TV" → rewrite as short standalone sentences/fragments). A colon before a genuinely short, idiomatic 2-item pair (on/off, yes/no) is fine and doesn't need converting.

**No storytelling preambles or scene-setting before the fact/product** ("There's a particular kind of X that...", "X is one of those Y where..."). This also includes tricolon/parallel-clause rhythm even without narration ("Walls get painted, shelves get styled, furniture gets picked out carefully..." or "no paint, no primer, no drilling" — three parallel clauses building to a punchline is the same trap). A dense sentence linking 3 things (e.g. 3 sibling posts) that gives each its own descriptive clause is this same trap wearing a comma disguise — the fix is dropping individual per-item description entirely or restructuring so only one gets a clause, not just re-splitting into shorter sentences with the same three-beat rhythm.

**No reaching for cleverness** — stock idioms ("doing double duty"), blogger-jargon ("a real style moment"), cute wordplay/personification for a punchline ("the table just gave up," "wearing a nice cushion") are all the same trap in different clothes. This is a distinct proofread lens from voice/storytelling checks, run it separately even after those pass clean. Test: would someone who's used this for a year say it out loud, unprompted?

**No interior-design-blog jargon** — a further distinct lens: "anchor" (a wall/room), "statement piece," "cohesive," "negative space," "faceted," "elevate," "curated," "effortless," "aesthetic" (as a noun), "moody," "editorial," "studied, collected feel." Reads polished and correct while being unnatural for what a regular person says about their own home ("$300/hr copywriter" test). Watch for the same jargon word behind a different noun ("statement vase" still fails on "statement" — search the word, not the exact phrase). Check award/badge fields too, not just body prose.

**Sentence economy in both directions:** neither a single half-line fragment nor a 3-line run-on stuffed with comma-joined examples. Real target is 2-3 normal-length sentences (~15-25 words each), each carrying one job, connected with real transitions (but, so, which, -ing clauses) — not just commas repunctuated into short choppy fragments (that fixes the run-on but creates a new, equally-wrong staccato problem).

**Category subheads:** real editorial H2s, never generic labels lifted straight from competitor research, never prefixed with the post title ("`<Title> for <X>`" reads like keyword stuffing), must be factually true of every item under them, must never repeat verbatim across sibling posts in the same cluster (derive a genuinely different organizing principle, don't just rename the same buckets), must not pair a category with something that's already a subset/synonym of it ("Bedding & Textiles" — bedding IS textiles). All subheads in one set should share the same grammatical form (all noun phrases, not a mix of noun-phrase and gerund-phrase). For gift-guide-style clusters specifically, subheads must be recipient-anchored ("Romantic and Sentimental Gifts for Girlfriend"), not abstracted.

**Titles and intros fail via cross-post skeleton reuse, checked separately from cleverness** — before finalizing, grep the actual live titles+intros of every already-published sibling in the same topic cluster (not just recall the rules abstractly); this recurs at every structural level (word → phrase → paragraph-skeleton → title-skeleton) even after being fixed once at a lower level. When a title keeps failing, the fix is usually to make it more boring, not more inventive. The frontmatter `description` and `answer` fields need this exact same cross-post AND within-post check — they're user-facing (post cards, AEO callouts), not just invisible metadata exempt from the anti-template rules. `description` also has a hard technical ceiling: ~155-160 characters (Google's truncation point), and must contain the actual target keyword phrase.

**Two per-product formats exist, pick deliberately:**

1. **Idea-first (now the sitewide DEFAULT for all new content, not gated behind competitor research)** — headline is the action/tip itself ("Hang curtains higher than the frame"), never a "Best X for Y" superlative. Body: idea + reasoning → name the real product as the means to execute it → what the idea accomplishes. Zero verdict/quality-judgment language, zero award/whofor-style review framing. Full checklist every entry must pass simultaneously (script-audit the whole batch, reactive one-at-a-time fixing does not propagate backward): no banned words; no "instead" as a standalone transition; direct you/your address; a genuine personality/reaction beat (not just mechanically correct-but-flat, this is its own separate check — fixing structure does NOT fix voice, do one more full read asking only "does this have a genuine reaction"); action leads the second paragraph, not the product as grammatical subject; no noun repeated 3+ times within one entry; correct grammar (no comma splices, no dangling pronouns); a distinct opening verb per product name across the whole post (don't let "Add" hit 48% of titles). `whofor` and the description's first sentence must never restate each other near-verbatim — whofor is a short scene-setting tag, the description must add genuinely new framing.
2. **Review format** — used when a topic is a genuine gadget/gift comparison-shopping category. Three-paragraph structure: problem stated plainly → product enters by its natural short name (not always sentence-first, vary position) → experience described before the feature that causes it → a genuinely new secondary value in the closing paragraph, not a restated point. Pros ≥ cons always (3-4 pros, 1-2 cons), vary the actual counts batch to batch, no two adjacent products share the same pair. Verdicts are exactly two sentences with a real judgment/trade-off, not a rephrased benefit tagline. Every description circles back to an explicit "This [product]..." callback tying the hook to the specific named item. Vary each batch's opening-sentence construction genuinely (scenario, short fact, negation, question — never a bare pronoun with no stated subject yet, never "This/These [product]..." as literally every paragraph-2 opener, never a bare feature/part as the grammatical subject of paragraph 3). Write to the reader ("you/your") but selectively, not mechanically in every sentence. The governing meta-rule after many rounds of correction: derive each description from the actual product's real frustration/appeal, don't imitate a previous product's shape or a rule's example sentence — the reader should think "that's exactly what I'd say," never "that's a well-written description."

**Audit discipline, past ~15-20 products:** manual read-through does not scale — write a script that counts first-word/opener matches per paragraph slot, banned-word instances, noun-repeats, etc., BEFORE presenting a draft, not after a complaint (`scripts/audit-idea-post.mjs <slug>` exists for idea-first posts — but it only checks the `products` JSON array; banned words/jargon/skeleton-reuse in frontmatter, intro, FAQ, and Final Thoughts need a separate whole-file grep and manual fresh read every time, a clean script run is necessary but not sufficient). Re-run the counter after every fix pass — a fix for one template trap can create a new one at a worse rate than the original (an "It" paragraph-opener fix once overshot from the original problem to 22/28 instances). **A full proofread means a genuinely fresh top-to-bottom read of every single product, not a word-frequency cut** — each flagged-word instance must individually earn its place, not just hit a lower count, and a fresh read catches comma splices/grammar errors/logic errors a frequency pass never will. Run these as separate lenses in the same pass, they don't overlap: clever-sentence, storytelling/tricolon, jargon, human-voice/awkward-flow, and (per the owner's own explicit 6-point definition of "proofread this") personality, human voice, American-audience voice, no awkward sentences, no thin one-liner paragraphs, 2-3 lines per paragraph. **When a passage still "reads terrible" after 2 patch rounds, do a full rewrite in one pass, not a third targeted patch.** When told to re-check something already reported fixed, do a genuinely fresh full read — each edit pass can introduce new problems (dangling pronouns, broken agreement) in sentences it didn't directly touch, invisible to a targeted diff review.

## Content production process

Full step-by-step production workflow (sourcing batches, writing, FAQ/Final Thoughts structure, internal linking, cover, pin, pre-push checklist, Pinterest posting mechanics) lives in **`FOUNDATION.md` → "Real post production workflow," Phases 1-9** — read that in full before producing a real post, this file only adds what isn't there or has drifted since.

- **Write copy straight into the real `content/posts/*.md` file as you go, batch by batch** — never paste draft copy into chat as "the deliverable," the file (or a dev-server preview URL) is the only real deliverable.
- **A batch isn't done until its images are physically copied into `public/products/` (or `covers/`/`pins/`) with descriptive filenames AND converted to webp** (`node scripts/convert-webp.mjs`) — a frontmatter path pointing at a file that doesn't exist yet is a broken post.
- **Check every new product/image name against `public/products/` before naming a file** — a generic filename can silently collide with an existing file from a different post; `convert-webp.mjs` skips conversion if a `.webp` with that name already exists, no warning, so the new image can sit unconverted while the post's frontmatter points at someone else's old photo.
- **Never bulk-delete a `product-drops/`/`pin-drops/`/`cover-drops/` folder**, even once every image in it is confirmed copied into `public/` — the owner reuses the raw files for pin-making later. Delete only individually-identified bad files, or ask first. `rm` in Git Bash bypasses the Recycle Bin entirely, no recovery path.
- **Background-removal is never a code fix.** The site's white product-card background is pure CSS (`object-fit: contain` on a white well); a lifestyle-scene product photo gets fixed by the owner regenerating a white-bg version of the same real product via their own AI image tool, not by installing background-removal tooling. Exception: rugs, bedding, curtains are legitimately shown in room context sitewide already. A genuine partial mitigation that IS allowed: `sharp` can crop tighter around the real product's actual bounding box (go tighter than feels natural on the first pass — a first attempt that only trims empty margins reads as barely changed).
- **Claude cannot fetch Amazon (503-blocked) or generate real `amzn.to` links** — give short, specific, single-concept search terms and wait for the owner to supply real links.
- **Cover and pin review must match every depicted product to its real numbered item for that specific category/section**, using a real distinguishing visual detail — not just "does this look plausible for the room." A cover/pin can pull in a real product from a DIFFERENT article entirely (stale reference images in the same AI generation session) — always state "use strictly the attached reference images, invent/substitute nothing" in every prompt. A pin can show all-real products yet still contradict its own room/category badge with items from the wrong section of the SAME post.
- **Never guess a post's live URL for a pin Link field or any on-site link** — verify the real route in `src/App.jsx` (real shape is `/blog/<slug>/`, not a bare `/<slug>`) every single time; a wrong link fails silently for a real visitor with zero error anywhere in the workflow. `scripts/check-pin-links.mjs` live-verifies.
- **Never push a post without cover + pin-1 already wired**, unless explicitly told to push without them.
- **After retitling an already-published post, grep the whole repo for the old title string** — sibling posts usually use short anchor text so only the pillar's structured list typically needs fixing, but verify, don't assume.
- **Confirm before implementing: get explicit go-ahead before touching CONTENT-PLAN.md, and consent from one batch never carries to the next** — ask again every time, even mid-task, even when the process feels established. This applies doubly to anything structural/architectural (URL schemes, data models) — state the recommendation, then ask, don't treat a converging conversation as authorization.
- **`git add` with a glob against a large directory can fail "Argument list too long"** — add the whole directory instead, git only stages what actually changed.

## Post structure rules

- Section order: intro prose → `<!-- products -->` marker → `## FAQ` → `## Final Thoughts`. The marker must sit after the intro and before the first trailing section — prose below it silently doesn't render as the intro.
- **No "## How We Chose" section, ever** — duplicates the sitewide disclosure line already in every post's header, go straight from products into FAQ.
- **FAQ must use the real `<details><summary>Question</summary>Answer</details>` accordion markup** — never plain bold-text — and every question must be a specific fact tied to a real product in THIS post's list, never generic filler that could apply to any article on the topic. Check a live sibling post's raw FAQ markup before writing a new one, don't recall the format from memory.
- **Always give the closing paragraph its own `## Final Thoughts` heading** — a floating unheaded final paragraph reads unfinished.
- Check the primary keyword landed in the body (title, meta description, AEO answer, intro's opening line — 4 instances minimum) every single post, it does not carry over automatically from the last one.

## Internal linking

- Every spoke links to its pillar, always, plus one sparse natural inline sentence linking every already-published sibling in the same cluster (not a bulleted list, and not just 1-2 siblings — every one published so far, accumulating as new siblings publish).
- The pillar links to every spoke via a structured `## More [X] in This Collection` bullet list below Final Thoughts — **this structured list is pillar-only, never on a spoke.**
- **Hard rule: never link across a category boundary**, even when a keyword overlap makes it tempting. If a pillar has no published same-category siblings yet, it gets zero internal links for now — no cross-category substitute.

## Sub-topic page gate

**Never build a category sub-topic (Kitchen Organization, Small Space Ideas, etc.) its own dedicated page until it has ~4-5 real posts.** This is enforced in code (`Topic.jsx`, `MIN_POSTS_FOR_TOPIC_PAGE` in `content.js`) — a topic chip on the category page is a clickable link once `postsInTopic()` returns results, or an inert greyed-out span until then, so the gate self-enforces. The category page groups its post grid by topic once a category has more than one topic; the homepage stays a pure reverse-chronological feed always, never grouped.

## Pin / cover creative direction

- **Covers use one locked template, only the accent color varies** (pick a color not yet used in the same content cluster): number + bold serif headline + script subtitle baked into the image as text, dense grid of real products with real visible brand logos (fine, not excluded), thin single-color border, warm cream background, no photographic scene. Real dimensions are **1672x941** — verify via `sharp`'s `.metadata()` against an actual existing file, never guess or use a rounder "convention" number. When a single-room-scene template is used instead for a themed multi-room post, pick the room that reads smallest/most cluttered by default, not the category with the highest product count.
- **Pins are the opposite: every pin must be a genuinely new visual campaign, never a reskin** — composition, hierarchy, typography, mood must all feel unique; changing only colors/fonts/positions does not count as new. Check real existing pins in `public/pins/`/`pin-drops/` before proposing a layout, not from memory. Even a thorough standing instruction to the image tool can still drift across a long single-session batch (confirmed real: pins 7-10 of a 10-pin run converged on the same layout after pins 1-6 held the line) — generate in smaller sub-batches of 4-5 and compare the on-image caption TEXT side by side (not just the visuals) to catch repetition. Build the pin around ONE integrated real room/scene, never segmented multi-panel layouts, even for a topic covering multiple distinct sub-categories. Winning CTA formula: a specific named-count CTA ("32 IDEAS INSIDE," not "learn more"), a "SAVE THIS PIN" badge, a deliberate domain banner (not a bare afterthought line), real font-weight hierarchy (serif numeral + bold headline + script subtitle as 3 distinct weights).
- Pin title: front-load the real keyword in the first 40 characters (max 100). Pin description: target 200-300 characters, not the 500 max — padding toward the max doesn't help, the first 50-60 characters are what shows before truncation. Alt text: cap ~125 characters, literal/descriptive for accessibility, never a reused copy of the description.
- **Never verify a pin's depicted products against the real post's product list before giving posting details** — the owner decides pin quality by eye, this would waste their time. Cover/pin review for CONTENT-ACCURACY (matching numbered items, cross-article contamination) is still the real job when writing/reviewing the post itself; this exception is specifically about not re-checking before a Pinterest posting recommendation.
- **Add any new post's slug to `pin-tracker.mjs`'s `CLUSTERS` mapping at the exact same step as wiring cover/pin** — an unmapped slug throws a deliberate fail-loud error rather than guessing a board, and this gap has recurred repeatedly by being left for the crash to catch instead.
- Pinterest posting mechanics, round-gating, and live status: run `node scripts/pin-tracker.mjs` fresh every session, never trust a saved snapshot. Durable rules the script doesn't encode: pin-1 always posts before pin-2 for the same post (but verify with `node scripts/check-pin-duplicate.mjs` first — the tracker's count can drift from which file is actually live); no cross-post blocking otherwise — a post at level 3 can post pin-4 the same day another post is still stuck at level 0, as long as they're not fighting over the same board; same-day-same-board repeats are banned, different boards same day is fine; every pin needs all six fields (Title, Description, Link, Board, Tagged topics, Alt Text) — Tagged topics is never left blank.

## Design review

- **Never offer written design options to this owner — they decide only from what they can see.** Build it (or a real mockup off the dev server), screenshot at 1440 and 390, hand over the URL. A described option is not a decision they can make.
- Screenshot the current state and name concrete measured defects before proposing anything ("the first guide doesn't appear until 2,700px down on mobile," not "it feels off").
- Expect blunt rejection of anything that's just a tidied version of the existing template — "redesign" means a different layout, not a cleanup. Feedback arrives incrementally as they look at it; fix and re-screenshot immediately, don't batch or argue.
- Measure before fixing a layout bug (`page.evaluate` + `getBoundingClientRect`) rather than guessing at flex/grid causes.

## Niche & audience

Product roundups + gift guides, home/kitchen. Amazon SiteStripe images (real, legitimate, free) — zero original photography. Audience is mostly female, US/UK/CA/AU; owner wants only tier-1 country traffic (bad prior experience with low-tier bot/junk traffic on a different project) and watches GA4 for spikes once real traffic exists — remember an AI-crawler-citation strategy (AEO) can't be geo-restricted, that's a known, accepted tradeoff, not an open problem.
