## Design (as actually built — supersedes any earlier mockup)

### Design language — read before touching any page; reuse these moves, don't invent new ones
**Status: work in progress, not final.** The owner considers the current design maybe halfway there and expects to keep tweaking it session by session. So: the rules below are the stable foundation to build on (don't contradict them casually), but expect ongoing refinement requests on top of them — spacing, copy, individual sections, new polish. When a tweak conflicts with a rule below, ask or update the rule here; when a tweak is just refinement, apply it and keep this section current.
1. **Mood:** warm editorial magazine for a shopping guide. Think curated print catalog. Never review-lab (no "tested/methodology" visuals), never SaaS landing page (no rounded gradient blobs, no emoji).
2. **Sharp corners everywhere.** `border-radius: 0` on every element — cards, buttons, inputs, images, chips. The single exception is the circular founder portrait.
3. **Surfaces:** page background is warm paper `#FAF8F4`. Content cards are pure white with 1px `--line` hairline borders — white is reserved for content surfaces so they read as cards against paper. Tinted panels use `--paper2 #F2EEE5` or the butter-pale gold wash. Never flat-white the page background; that was tried and it made every tinted panel look like a dirty gray box.
4. **Full-bleed band system:** homepage sections alternate background bands via `.band` (`margin: 64px calc(50% - 50vw)` breakout + inner `.wrap`; `html,body { overflow-x: clip }` prevents scrollbar overflow). Variants: `.band-white` (hairline top/bottom borders), `.band-spruce`, `.band-butter`. The page is framed in ink: slim `.topbar` at the top, dark footer at the bottom. Sections read as distinct rooms; don't stack floating boxes on one background.
5. **Color roles, strictly:** Ink `#14130F` = text and the two framing bands. Spruce `#1D5235` = everything interactive and brand-voiced: links, buttons, tile icons, the one italic accent phrase in the hero H1, the founder band background. Gold `#C9A030` = ornament only — eyebrow rules, diamonds, keyline frames, chips, italic numerals, hover arrows, topbar ✦ marks; never a large fill, and small gold text on light backgrounds uses `--butter-ink #7A5B14` for contrast.
6. **Typography:** Fraunces weight 500 for every heading; Fraunces italic for accent phrases and decorative numerals ("No. 1"); Inter Tight for everything else. One eyebrow style sitewide: `.lbl` (12px/600/.08em/uppercase). Every size comes from the `--fs-*` scale in `:root` — never set a one-off px size.
7. **Signature moves** (the recognizable SavvyHomie details): small-caps eyebrow flanked by short gold rules, above a serif Title Case H2 (`.sec-head`) · gold diamond-with-rules ornament (`.hero-orn`) · branded placeholder art for missing images (paper2 + inset gold keyline + thin-line house logomark + "Photo via Amazon") · oversized faint gold house outline on dark bands (`.founder-orn`) · gold `::selection` tint.
8. **Motion:** hover-only, subtle. Cards lift 2px + soft shadow; cover images zoom `scale(1.03–1.05)` over .25–.3s; arrows slide in on tile bars; color/background transitions .15s ease. Every transform sits behind a `prefers-reduced-motion` guard.
9. **Alignment rhythm:** homepage sections and article headers are centered; body copy and card interiors are left-aligned; never mix alignments inside one section.
10. **Buttons:** `.btn` solid spruce, hover darkens to `#17452C` (never opacity fades); `.btn-ghost` butter-ink outline, hover fills. Text links in spruce with a trailing → for "read/browse" actions. **Inline links inside body copy are always spruce + bold (600) + underlined** (underline-offset 2px) — one shared rule covers `.prose`, `.disclosure`, `.about-story`, `.about-money`; extend that selector list when new body-copy surfaces appear, never invent a second inline-link style.
11. **Ads/affiliate constraint:** content always sits on white or paper (ad creatives and Amazon product shots assume light backgrounds — same reason as the no-dark-mode rule). Keep `.ad-slot` divs where they are and dimension-quiet (no CLS).
12. **Verification is part of the language:** no visual change is done until screenshotted at 1440 AND 390 (`node scripts/screenshot.mjs <url> <out.png> [width]`) and actually looked at. The hero-sub misalignment shipped because a wide-viewport check was skipped.

Paper `#FAF8F4` · Card `#FFFFFF` · Ink `#14130F` · Muted `#6B6862` · Soft `#4A4843` · Gold accent `#C9A030` (used sparingly — chips, CTAs, small rules, never as a fill everywhere) · Spruce green `#1D5235` (links, buttons). ## Content workflow (agreed, not yet run for real)

## Tech stack (as built)

Client-side navigation is fast (React Router `Link`), same pattern every sibling project uses (Zennara/react-router, workwithdenzil/Next.js Link).

- **Dev server:** `npm run dev`. **Port 5173 is taken by the user's other project (ytgrowth) on this machine — always use `--port 5180`** or you'll silently hit the wrong app.
- **Hosting:** Railway (auto-deploys on git push) with Cloudflare in front for DNS. No WordPress, no Astro (explicitly rejected).
- **Content:** Markdown files in `content/posts/*.md`, custom frontmatter parser in `src/lib/content.js` (supports multi-line JSON arrays for the `products` field).
- **Screenshot/visual verification:** Playwright is installed ad hoc (`npm install --no-save playwright pngjs` — not in package.json, reinstall each session) with `scripts/screenshot.mjs`. ## Content production decisions (2026-07-22, before real writing starts) — read before writing any real post

**Image sourcing for "ideas"/inspiration posts (Cozy Bedroom Ideas, Small Space Ideas, Cottagecore Decor, etc.) — same Amazon-only rule as everything else, no exception.** Never pull a Pinterest image and modify it to use as a post image, even for full-room "inspiration" style content. Pinterest pins aren't free-to-use just because they're publicly visible — they're pulled from somewhere (a blog, a stock site, a designer's portfolio) and stay under that original owner's copyright, so reusing/modifying one is real copyright infringement risk and directly undercuts the E-E-A-T/trust angle Carol's bio is built on. This isn't actually a hard problem: every post on this site, including "ideas" posts, follows the same 10-15 product roundup format ("Cozy Bedroom Ideas" = 15 products that create a cozy bedroom look, each with its own real Amazon SiteStripe photo) — there's no full styled-room photo needed, the individual product shots are the visual content. If a post ever genuinely wants a full lifestyle/room hero shot beyond product photos, use legitimately licensed free stock photography (Unsplash/Pexels — both grant explicit commercial-use rights) instead, never a repurposed pin.

**Pillar posts go bigger than spokes (decided 2026-07-22, first applied to the Christmas Gift Ideas pillar).** Real competitor research (actual word count + item count, not a search-summary guess) showed top-ranking Christmas gift roundups running 42-50 items and 3,500-5,500 words, against our original 10-15 item/1,500-word standard. Owner's call: match that depth on every pillar going forward, not just this one — "we have to be safe, we can't leave anything." **New standard: pillar = 40-50 products, 3,500-5,000+ words; spokes stay at the original 10-15 products/1,500+ words** since they target narrower keywords where competitors aren't running nearly as deep. Also updated in CONTENT-PLAN.md's top rule.

**Supporting/secondary keywords come from the existing gap-analysis workflow step, not a fresh Keyword Planner pull per post.** The content workflow (see "Content workflow" section above) already includes "study top 10 Google results + Pinterest for that query, gap analysis: what they covered, what they missed" — that read is where supporting keywords, subtopics, and FAQ questions naturally surface. This matters most for DIY/organize posts (mixed Google+Pinterest traffic, broader topical coverage helps Google ranking). For pure Amazon-roundup content (Pinterest-only, no Google-ranking expectation), supporting keywords matter less for ranking and more for writing a genuinely complete, useful post — same gap-analysis read covers it, no separate Planner pull needed per post. The single primary keyword per post is already locked in CONTENT-PLAN.md from the keyword-mapping pass; this step is about supporting depth, not finding a different primary keyword.

**Product description tone: vary sentence structure, don't lean on the same rhetorical crutch every time.** Caught 2026-07-22 on the first real batch — nearly every product description used the same "X, not just Y" or "sounds like a brag until it's actually Z" reveal-the-hidden-truth structure back to back, which reads as an AI-generated pattern once you see 6+ in a row (same failure mode the site's writing-style rule already warns about). Vary the opening move: some start with a scenario, some with who it's for, some with a plain fact, some short and direct. Check a batch's descriptions against each other before moving on, not just each one in isolation.

**Product card writing rule: pros count must always be ≥ cons count, never let cons outnumber (or just match) pros on a recommended pick.** Caught 2026-07-22 on the first real batch (Christmas Gift Ideas pillar) — a couple of products ended up with 3 cons against only 2-3 pros while varying the counts away from a rigid 2-and-2 template, and that reads as undercutting our own recommendation, not "honest curation." Vary pros/cons counts for genuine variety (not every product needs exactly 2 and 2), but always keep pros ≥ cons.

**Product images: screenshot the real Amazon listing page instead of using the small SiteStripe thumbnail.** Caught 2026-07-22 on the same batch — SiteStripe thumbnails are often only 300-500px (some listings just don't have a bigger master image, confirmed by requesting larger sizes from Amazon's own CDN and getting back the identical file), which visibly blurs once displayed at product-card width. A full screenshot of the listing page is much sharper. Product card image display was also changed from full-bleed stretch-to-fill to a centered/contained image on a white background (`.product-photo-well`, matches `.product`'s own white card background so a white-background product photo blends in with no visible box/seam, plus a thin `border-bottom` divider so it doesn't merge invisibly into the text below).

## Real post production workflow (recorded 2026-07-22, updated 2026-07-23 after Gifts for Wine Lovers + Christmas Gifts for Coworkers) — follow this exact sequence for every future spoke/pillar, in order

This is the actual end-to-end process, refined across three real published posts (Christmas Gift Ideas pillar, Gifts for Wine Lovers, Christmas Gifts for Coworkers). Nothing here is theoretical — every rule exists because skipping it caused a real, specific mistake that had to be caught and fixed. Read this whole section before starting a new post; don't re-derive the process from scratch or let it drift session to session.

### Phase 1 — Research and planning (before sourcing a single product)

1. **Competitor research happens per post, not just for the pillar.** Pull 4-8 real top-ranking pages for the exact keyword (WebSearch to find them, WebFetch to pull real item counts/structure — expect some fetches to 403/451, that's normal, just get enough real data points from what does load). Record item count for each source, then **explicitly discard sources that aren't real competing editorial content**: a business's own product catalog page, a retailer's storefront, or a guide that's 80% padded with unrelated occasions (a "gifts for coworkers" mega-post that's mostly birthday/thank-you/sentimental content isn't a fair comparison for a Christmas-specific post). The real target is the median of genuine editorial guides, not the highest or lowest outlier. This has produced 20-33 items for spokes so far, well above the naive "10-15" default — always verify per keyword, never assume the default holds.
2. **Build the product/category list, then self-audit it for hidden duplicates before showing it or shopping from it.** Two near-identical items dressed as different categories (three separate "insulated drink vessel" entries; a "hand cream set" next to a "spa set" that already contains hand cream) read as padding once written up. Check every proposed item against every other one for overlapping function, not just overlapping name.
3. **Give the category → Amazon search-term list up front, categorized.** This is what the owner shops from. Keep search terms generic/descriptive (never a brand name), and word them precisely enough that they can't accidentally return the wrong product class — "phone stand" alone pulled a tripod, "holiday ornament" alone pulled ornament storage. Specify the distinguishing word ("desktop phone stand," "personalized Christmas ornament, not storage") whenever a term is genuinely ambiguous on Amazon.
4. **Pick a real title before writing anything, and get the number right.** Never use the raw CONTENT-PLAN.md keyword as the title — that field is explicitly the validated keyword, not headline copy. Write a real hook (a number + a benefit angle), and make sure the number matches the *actual final* product count, not a planning-stage guess. If the count changes mid-build (it will), fix the title immediately, don't leave it stale.
5. **Check whether the keyword itself should include a seasonal qualifier — verify from CONTENT-PLAN.md, don't assume.** Some spokes in a seasonal cluster validate with "Christmas" in the keyword (Christmas Gifts for Coworkers), others validate as evergreen even though they're written for seasonal traffic (Gifts for Wine Lovers has no "Christmas" in its own validated keyword). Match whichever the real keyword research found, and keep the title consistent with that — an evergreen keyword doesn't need Christmas-specific framing forced into the title or cover art.

### Phase 2 — Sourcing and writing, batch by batch

6. **One category = one subfolder, `product-drops/<post-slug>/batch-N-<category>/`.** Before writing a single word of copy for a batch: count images in the folder against links sent, and view every image to confirm it actually matches what was requested — not just that a file exists. This has caught real mismatches every time it's been skipped: a decanter dropped in place of an aerator, a DIY engraving tool dropped for "engraved pen set," a tripod for "phone stand," an ornament storage box for "holiday ornament," and — most commonly — an entire previous batch's leftover images sitting unnoticed in a new batch's folder alongside only one or two genuinely new ones. If a batch folder has more images than the current batch needs, that's the leftover-file signal, not a bonus.
7. **Write copy per batch and self-check that same batch immediately — don't wait for a final pass.** Per product: pros ≥ cons always (never equal, never fewer), 3-4 genuine pros minimum, and vary the actual pros/cons counts so no two *adjacent* products in the whole post share the same pair (check against the previous batch's last product too, not just within the new batch). Vary description length deliberately from the very first batch — a real spread across the whole post ends up roughly 15-20% one-sentence, 60-70% two-sentence, 15-20% three-sentence; writing every single description at a uniform length (all 24 at exactly two sentences, discovered after the fact once) reads as templated even when each one looks fine in isolation. Vary opening sentence structure the same way. Run a real grep for em-dashes, "actually," and "really" after *every batch*, not just at the end — this has caught stray instances in whofor fields, verdicts, and even award titles ("Best for Actually Packing Lunch") that a single end-of-post pass would otherwise have to catch all at once.
8. **When a sourced product doesn't match its intended slot, decide explicitly, don't silently write around it.** Either the owner swaps it (ask what the search-term ambiguity was, fix the term, re-source), or the owner says to keep it and copy gets written honestly for what the product actually is, never dressed up to sound like the originally-requested item.
9. **Run the audit as an actual script after every batch, not a manual read-through:** a `node -e` one-liner checking pros/cons counts, adjacent-duplicate pairs, and (once the whole post is done) description sentence-length distribution and exact keyword-instance count. This is dramatically cheaper than one big end-of-post audit that has to re-read everything, and it means each batch ships clean before the next one starts.

### Phase 3 — Structure (apply once, the same way, every time)

10. **No "How We Chose" section, ever.** It duplicates the sitewide "How we pick products" link already in every post's disclosure line at the top. Go straight from the product list into the FAQ.
11. **FAQ questions must be specific to the actual topic, not generic gift-guide boilerplate.** "What's a good budget" and "what if I don't know their taste" could sit on literally any gift guide on the internet — write toward the real, specific anxiety of *this* recipient/topic instead (for wine: the expertise gap, gadget-vs-bottle, already-owns-everything; for coworkers: the "not trying too hard" line, whether to include the boss, the same-gift-to-the-whole-team question).
12. **Always give the closing paragraph its own `## Final Thoughts` heading.** A floating final paragraph with no heading reads as unfinished next to every other properly-headed section.
13. **Check the primary keyword landed in the body, not just title/meta — every single post, every time.** Grep the finished file for the exact keyword phrase. Target: title, meta description, the AEO answer callout, and the intro's opening line, at minimum (4 instances). This has been missed on the very post immediately after fixing it on the previous one — it does not carry over automatically, check it explicitly per post.
14. **Vary the meta description's opening across posts.** Two posts in a row both starting "Real [topic] gift ideas for..." is the same templated-opener problem as description sentence structure, just at the post level instead of the product level. Check the previous 1-2 posts' actual meta descriptions before writing a new one.

### Phase 4 — Internal linking (once more than one real post exists in a cluster)

15. **Every spoke links to the pillar in its intro, with real anchor text, not just via the automatic same-category related-posts card.** The related-posts mechanism is a helpful baseline (same category, excludes self, shows up to 3), but a deliberate in-body link carries more weight and reads better to an actual reader.
16. **Sibling-to-sibling links stay sparse, not a full mesh (revised 2026-07-23).** The original rule called for a "full triangle" (every spoke links every other spoke) — that only works at 2-3 spokes. The Christmas cluster alone is headed for ~19-29 spokes (see CONTENT-PLAN.md), and no spoke's intro should try to link a dozen-plus siblings. Each spoke links to the pillar always, plus 1-2 siblings **only where there's a genuine natural bridge** (Teacher Christmas Gifts → Gifts for Wine Lovers, because "what if the teacher likes wine" is a real connection), never an exhaustive list just because siblings exist.
17. **The pillar links to every spoke, but in a structured list, not prose (revised 2026-07-23).** Standard hub-and-spoke SEO wants the pillar (usually the highest-authority page in a cluster) linking to *all* its spokes, not a sample — that's what distributes link equity and signals topical comprehensiveness to Google, and skipping most of them would actively hurt those spokes' ability to rank. But cramming 29 links into one Final Thoughts sentence reads as spam and risks unnatural-link-density signals. The fix: keep Final Thoughts short and narrative with no links, then add a separate `## More Gift Guides in This Collection` heading below it with one bullet per spoke (`- [Title](/blog/slug/), short context`). This is plain markdown, no new component needed — it renders through the existing `.prose` list styling. Add a bullet every time a new spoke in that cluster publishes; this scales to any number of spokes without restructuring. See `christmas-gift-ideas.md`'s Final Thoughts section for the reference implementation.

### Phase 5 — Cover image

18. **Real Amazon product photos are always safe; AI generation is allowed only for the cover/pin images specifically, with an explicit locked-product-list prompt** (no invented items beyond the named list, no brand logos, no text overlay on the cover specifically, exact aspect ratio stated). This is a deliberate, narrow exception to the site's Amazon-only image policy — the products depicted are still real, nothing else about the "no external images" rule changes.
19. **Match the cover's background styling to whether the topic is actually seasonal.** A Christmas-titled post (Christmas Gifts for Coworkers) can use string lights, pine, pinecones. An evergreen-keyword post that just happens to be timed for Christmas traffic (Gifts for Wine Lovers) should get a season-neutral background (candlelight, plain wood table, no pinecones/holly/string lights) — a heavily Christmas-decorated cover on an evergreen post looks mismatched to anyone who finds it in March. Say this explicitly in the prompt; it does not happen by default, and copying a prompt from a genuinely seasonal post's cover onto an evergreen one's is a real, repeatable mistake.
20. **Once approved:** copy into `public/covers/<slug>.<ext>`, add `cover: /covers/<slug>.<ext>` to frontmatter, run `node scripts/convert-webp.mjs`, then update the frontmatter path to `.webp`, rebuild, and confirm `og:image` picks it up in the built HTML.

### Phase 6 — Pinterest pin

21. **Pin prompts and cover prompts are opposites on text overlay — do not reuse one for the other.** Covers get no text (the title renders separately as HTML on the page). Pins need bold text overlay baked into the image — this is the established, proven pattern (a number, a headline, a script sub-line) that measurably outperforms photo-only pins on Pinterest, and it's why the pin that was actually approved and shipped had text and the ones that got rejected mid-session as "terrible" were built from a prompt that said "no text overlay," copied by mistake from the cover-prompt pattern.
22. **A short prompt ("same style as before") only works inside the *same* ChatGPT conversation thread that has that style in its context.** In a fresh thread it has nothing to anchor to and the result is genuinely unpredictable — always ask which situation applies before assuming a short prompt will work, rather than re-blaming the prompt wording after the fact.
23. **Pin design is the owner's own manual work, not something to generate via CSS/Playwright.** A full session was spent trying to hand-build pins that way and every version was rejected — real high-performing reference pins use genuine styled photography and hand-lettering that CSS compositing over isolated ~300-500px Amazon product cutouts cannot replicate. Don't re-attempt this in a future session.
24. **When reviewing pin options the owner generated, compare against the real product list and calibrate severity honestly.** A wrong *brand label* on the otherwise-correct product type (a tumbler that says "Yeti" instead of the real "Coldest" brand) is trivial and barely worth mentioning. A wrong *product entirely*, or a product pulled from a different section of the post than the pin claims, is a real problem and should sink that option in favor of a more accurate one, even if the inaccurate one looks more polished. A pin that shows only 6-7 items but all real beats one that labels 25 items where half are invented.
25. **Once approved:** same drop-in process as the cover — `public/pins/<slug>.<ext>` → `pin: /pins/<slug>.<ext>` in frontmatter → `convert-webp.mjs` → update path to `.webp` → rebuild.
26. **The on-page pin embed is a collapsed, expandable `<details>`/`<summary>` ("Pin this list") right after the cover, not a permanently-invisible 1x1px element.** The owner explicitly wants readers to be able to see and manually save it, not just leave it as an algorithm-only hook. **Known layout trap:** the toggle is 920px wide inside an 840px reading-column parent (same deliberate overflow as the hero image), so it must be centered with the same explicit `calc()` margin-left formula the hero image uses — plain `margin: auto` silently resolves to `0` (not centered) once a box is wider than its containing block per the CSS spec, which rendered it 80px off-center on every single post with a pin until this was caught and fixed sitewide.

### Phase 7 — Pre-push checklist (run as a script, every post, no exceptions)

27. Every product has a real, unique `amzn.to` URL, no duplicates. Every affiliate link carries `rel="nofollow sponsored noopener"`. Every `#pick-N` lineup anchor resolves and the count matches the product count. Every image path ends in `.webp` and the file actually exists on disk. `readTime` is recalculated from the real final word count (not left at a placeholder set before all batches were written — this has been caught stale on every post so far, recalculate it as the very last content step). Canonical URL and `og:image` are correct in the built HTML. Sitemap `lastmod` is current. No em-dash/"actually"/"really" anywhere in the file. The primary keyword count is checked (Phase 3, step 13). Internal cross-links are verified in the built HTML (Phase 4), not just assumed from having written the sentence.

### Phase 8 — Housekeeping

28. **Delete demo/placeholder content the moment real content exists and the site has real traffic** — checked for hardcoded references first, confirmed empty-category states still render gracefully, then deleted outright.
29. **Git hygiene: stage deliberately, never `git add -A` blindly.** `.gitignore` covers the raw staging folders (`product-drops/`, `pin-drops/`, `cover-drops/`, `pin-references/`, `keyword-exports/`) and ad-hoc verification screenshots — none of these are consumed by the built site. Watch for genuinely stray debris too (a literal `$SCRATCH` directory once appeared in the repo root from a shell variable that failed to expand in one command) — check `git status` output for anything that doesn't look like a real deliverable before staging. Push triggers Cloudflare Pages' own git-integration auto-deploy; there's no local wrangler/netlify config, so a successful `git push` is the actual deploy trigger, confirm on the Cloudflare dashboard since this session has no API access to verify completion.
30. **Installing a new native-binding package (like `sharp`) can silently prune an existing dependency (`playwright`) from `node_modules` if it was never declared in `package.json`.** Re-verify tooling still resolves after any unrelated `npm install`, and make sure everything load-bearing is properly declared in `package.json`.

### Phase 9 — Pinterest posting mechanics

31. **Board/pin metadata is only ever written from owner-confirmed keywords, never guessed** — same rule as the board-optimization pass earlier in this doc.
32. **Board assignment logic:** a post's own dedicated board if one exists (Gifts for Him/Her have their own boards); otherwise the cluster's own board (Christmas Gift Ideas) for the general pin; the catch-all "Gift Ideas" board also fits any post whose recipient doesn't have its own dedicated board (coworkers, wine lovers) and is a good way to fill out that board specifically since it tends to sit thin.
33. **Posting cadence:** multiple fresh pins aimed at *different* boards can post the same day without it reading as spam, since it isn't repeated posting to one board's same audience. Multiple fresh pins for the *same* board should be spread across different days. When the same pin (or same post's general pin) needs to go to a second board, do it on a different day than the first posting, not the same day.
34. **Time zone conversion for scheduling (owner is in East Africa Time, UTC+3):** target roughly 8-11pm across US time zones (the majority audience) by converting to EAT — in US daylight saving months this lands around 3:00-6:00 AM EAT the *next* calendar day, which is really just "later tonight" carried past midnight, not a full day's wait. Always state an absolute date/time once this math is done, not another round of relative "tonight/tomorrow" language — that phrasing is what caused real confusion before.
